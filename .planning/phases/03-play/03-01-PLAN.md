# Plan 03-01: Dual Video DOM Infrastructure & Shaka Player Lifecycle Management

## Goal
Establish the core media rendering layers of the interactive video engine by implementing a dual `<video>` DOM recycling pool in React and integrating two persistent Shaka Player instances. This structure avoids constant DOM rebuilds and CPU spike overheads, laying the ground for seamless cross-fading and instant visual transitions.

## Must Haves (must_haves)
- [ ] `must_have_01`: Render exactly two static HTML5 `<video>` elements in the `InteractivePlayer.tsx` component, styled as absolute overlays with full coverage (`absolute inset-0 w-full h-full object-cover`).
- [ ] `must_have_02`: Configure CSS layering classes dynamically: Foreground has `z-index: 20`, `opacity: 1`, and `pointer-events: auto`. Background has `z-index: 10`, `opacity: 0`, and `pointer-events: none`.
- [ ] `must_have_03`: Instantiation of two persistent Shaka Player instances bound to Video elements inside a robust React `useEffect` hook.
- [ ] `must_have_04`: Complete memory leak prevention under React StrictMode double-mounting by utilizing an initialization lock flag and proper `.destroy()` cleanup calls.
- [ ] `must_have_05`: Integration of custom buffering and loading parameters to optimize Shaka Player instances for fast local MP4 playback.
- [ ] `must_have_06`: Replace the single-player container in `src/App.tsx` with the new `<InteractivePlayer>` component using the mock/sandbox state manager.
- [ ] `must_have_07`: Validation of TS compiling via `npx tsc --noEmit` and build completion via `npm run build` without failures.
- [ ] `must_have_08`: Introduce a `useNativeVideo` fallback state in `InteractivePlayer.tsx` to automatically downgrade to raw HTML5 video nodes upon fatal Shaka Player crashes.
- [ ] `must_have_09`: Validate Wave 0 TS compiler declarations in `src/shaka.d.ts` before starting actual player implementation to prevent namespace mismatch warnings.

<task id="03-01-01" name="Create InteractivePlayer React Component Shell and DOM Layering CSS Layout">
Implement the dual Video element layout structure in `src/components/InteractivePlayer.tsx`.

### Detailed Steps:
1. Create the `src/components` directory if it does not exist.
2. Build `InteractivePlayer.tsx` using Tailwind CSS classes for absolute styling.
3. Define React refs for both video elements: `videoRefA = useRef<HTMLVideoElement>(null)` and `videoRefB = useRef<HTMLVideoElement>(null)`.
4. Render both elements statically within a container:
   - Ensure the outer container has classes `relative w-full h-full overflow-hidden bg-black`.
   - Setup common video classes: `absolute inset-0 w-full h-full object-cover transition-opacity duration-[50ms] ease-linear will-change-[transform,opacity,z-index]`.
   - Setup conditional styles for Layer A and Layer B based on active player tracking state:
     - Foreground styling: `z-[20] opacity-100 pointer-events-auto`
     - Background styling: `z-[10] opacity-0 pointer-events-none`
5. Export the component and prepare properties for `NodeStateManager` integration.

### Verification Criteria:

- Confirm both Video DOM tags are permanently present in the React virtual DOM tree.
</task>

<task id="03-01-02" name="Initialize Shaka Players and Manage Robust Lifecycle Cleanup with Fallbacks">
Initialize both Shaka Player instances inside a React `useEffect` hook with safety guards against memory leaks, StrictMode re-renders, and critical player failures.

### Detailed Steps:
1. **Wave 0 type file validity check**: Inspect `src/shaka.d.ts` to ensure all custom typings compile cleanly under typescript config.
2. Import `shaka-player` inside `InteractivePlayer.tsx` and run `shaka.polyfill.installAll()`.
3. Define the React state `const [useNativeVideo, setUseNativeVideo] = useState(false)` inside the component.
4. Use `useRef` to store Shaka Player instances to avoid React-driven re-renders: `playerARef = useRef<shaka.Player | null>(null)` and `playerBRef = useRef<shaka.Player | null>(null)`.
5. In `useEffect` (triggered when `useNativeVideo` is false), use a lifecycle guard flag (`let isDestroyed = false`) to ensure cleanup works perfectly:
   - Perform browser capability check: `shaka.Player.isBrowserSupported()`.
   - Initialize both players: `playerARef.current = new shaka.Player(videoRefA.current)` and `playerBRef.current = new shaka.Player(videoRefB.current)`.
   - Configure buffering settings:
     ```typescript
     player.configure({
       streaming: {
         bufferingGoal: 6, // 6 seconds buffer goal for fast branches load
         rebufferingGoal: 2, // 2 seconds minimum buffer before play starts
         bufferBehind: 2 // Keep 2 seconds behind current play position
       }
     });
     ```
   - Register error listeners:
     - Listen to Shaka's `error` event. If a fatal crash occurs (`error.severity === shaka.util.Error.Severity.FATAL` or similar), log it and set `useNativeVideo(true)`.
   - Clean up on unmount: call `.destroy()` on both Shaka Player instances, and set `isDestroyed = true`.
6. **Fallback Rendering Logic**: If `useNativeVideo` is `true`, bypass Shaka Player instance mounting altogether, unload Shaka, and conditionally render standard HTML5 `<video src={videoUrl} />` tags in the component markup, preserving fallback high availability.
7. Integrate `InteractivePlayer.tsx` inside `src/App.tsx`. Define a mock configuration or plug it into `NodeStateManager` logic.

### Verification Criteria:
- Run `npx tsc --noEmit` to verify type checking.
- Inspect the browser console to verify Shaka Player instances are mounted exactly once (or cleanly re-mounted) under StrictMode without leaking memory or throwing multiple mounting errors.
- Test fallback behavior by manually mocking a fatal Shaka error event and verifying the system degrades cleanly to render a native video tag.
</task>
